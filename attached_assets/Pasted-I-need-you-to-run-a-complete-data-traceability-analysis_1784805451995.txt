I need you to run a complete data traceability 
analysis on the CareReward codebase and database. 
This is a compliance exercise. Read every relevant 
file and produce a traceability report.

Do the following in this exact order and do not 
stop until all steps are complete.

════════════════════════════════════════════════
STEP 1: SCAN ALL API ROUTE FILES
════════════════════════════════════════════════

Read every file inside lib/api/routes/.
For each file, identify every HTTP endpoint 
(GET, POST, PUT, PATCH, DELETE).

For each endpoint collect:
  - HTTP method
  - Route path (e.g. POST /api/points/allocate)
  - Every field read from req.body
  - Every field read from req.params
  - Every field read from req.query
  - Every field derived from req.userId (JWT)
  - Every field derived from req.headers

════════════════════════════════════════════════
STEP 2: MAP INPUTS TO DATABASE TABLES
════════════════════════════════════════════════

For each endpoint from Step 1, read the code 
carefully and identify:

WRITES (INSERT or UPDATE):
  - Which table is written to
  - Which column receives which input field
  - Which columns are auto-generated by the system
  - Whether the value is transformed before storage
    (e.g. password → bcrypt hash)

READS (SELECT):
  - Which tables are queried
  - Which WHERE conditions are used
  - Whether user_id from JWT is always applied
    as a filter (CRITICAL for data isolation)

════════════════════════════════════════════════
STEP 3: SCAN THE SCHEMA FILE
════════════════════════════════════════════════

Read lib/db/schema/index.ts completely.
List every table defined and every column in 
each table.

For each column note:
  - Column name
  - Data type
  - Whether it is nullable
  - Whether it has a default value
  - Whether it is a foreign key

════════════════════════════════════════════════
STEP 4: CROSS-REFERENCE AND FIND GAPS
════════════════════════════════════════════════

Compare what the routes write (Step 2) against 
what the schema defines (Step 3).

Find and flag:
  A. Columns in schema that are NEVER written 
     to by any route (potential dead columns)
  
  B. Fields in request bodies that are NOT 
     stored anywhere (data that is used but 
     not persisted)
  
  C. Routes that do NOT apply user_id filtering
     on SELECT queries (data isolation risk —
     critical security issue)
  
  D. Tables that have no corresponding API 
     route writing to them (tables that exist 
     but have no data entry path)

  E. Any route that reads from a table without
     a WHERE user_id clause where one would be
     expected

════════════════════════════════════════════════
STEP 5: CHECK HIPAA FIELDS ARE HANDLED CORRECTLY
════════════════════════════════════════════════

The following tables contain PHI 
(Protected Health Information):
  - connected_health_systems
  - emr_records
  - connected_devices
  - device_readings
  - copay_records
  - audit_logs

For each PHI table, verify:
  - Every SELECT on this table logs to audit_logs
  - The user_id filter is always applied
  - No bulk SELECT without a user_id WHERE clause
  - Raw PHI is not returned unnecessarily in 
    API responses (check what displayData vs 
    rawData returns)

Flag any PHI table route that is missing 
audit logging as a CRITICAL finding.

════════════════════════════════════════════════
STEP 6: VERIFY AUDIT LOG WRITES
════════════════════════════════════════════════

Find every place in the codebase where 
audit_logs is written to (INSERT).

For each write, confirm:
  - user_id is populated
  - action field describes what happened
  - outcome is either SUCCESS, FAILURE, or BLOCKED
  - timestamp is auto-generated

Find any endpoint that handles PHI but does 
NOT write to audit_logs. Flag each as CRITICAL.

════════════════════════════════════════════════
STEP 7: CHECK POINTS BUSINESS RULES IN CODE
════════════════════════════════════════════════

Find the code that enforces these rules and 
confirm each one is present:

RULE 1: current_balance can never exceed 
  earned_this_year
  → Find where this is checked
  → If not found: flag as CRITICAL

RULE 2: 1 point equals exactly $1
  → Find where dollar_value is calculated
  → Confirm: dollar_value = points_redeemed × 1

RULE 3: HSA ytd_contribution cannot exceed 
  yearly_limit ($4,400)
  → Find the validation check
  → Confirm the error message is returned to client
  → If not found: flag as CRITICAL

RULE 4: Points deduction only happens at 
  final confirmation (not at allocation)
  → Confirm points_accounts.current_balance
    is NOT updated at /api/points/allocate
  → Confirm it IS updated at 
    /api/points/confirm/final

RULE 5: Testing reset only works when 
  TESTING_MODE=true
  → Find the environment check
  → Confirm it returns 403 otherwise

════════════════════════════════════════════════
STEP 8: RUN THE UAT SCRIPT
════════════════════════════════════════════════

Copy the file uatRunner.ts into 
lib/testing/uatRunner.ts if it does not 
already exist there.

Install any missing dependencies:
  pnpm add -D tsx

Then run:
  npx tsx lib/testing/uatRunner.ts

Capture the full output.

════════════════════════════════════════════════
STEP 9: GENERATE THE TRACEABILITY REPORT
════════════════════════════════════════════════

Create a new file at:
  lib/testing/reports/traceability-[today's date].md

The report must contain these exact sections:

SECTION 1: EXECUTIVE SUMMARY
  - Total endpoints analysed
  - Total tables in schema
  - Total data fields traced
  - Critical findings count
  - High findings count
  - Medium findings count
  - UAT pass rate from Step 8

SECTION 2: ENDPOINT INVENTORY
  A table listing every endpoint with columns:
  Method | Route | Tables Written | Tables Read | 
  User Filter Applied | Audit Logged

SECTION 3: COMPLETE DATA TRACEABILITY MATRIX
  For every input field across all endpoints:
  Input Field | Endpoint | Transformation | 
  Destination Table | Destination Column | PHI?

SECTION 4: SCHEMA COVERAGE
  For every table in the schema:
  Table | Total Columns | Columns Written By API | 
  Columns Never Written (dead columns) |
  Write Endpoint | Read Endpoint

SECTION 5: CRITICAL FINDINGS
  Numbered list of every CRITICAL issue found.
  For each finding:
    - Finding ID (e.g. CRIT-001)
    - Description of the issue
    - File and line number where found
    - Risk if not fixed
    - Recommended fix

SECTION 6: HIGH FINDINGS
  Same format as Section 5 but for HIGH severity.

SECTION 7: MEDIUM FINDINGS
  Same format but for MEDIUM severity.

SECTION 8: BUSINESS RULES VERIFICATION
  Table showing each business rule, whether it 
  was found in the code, and where:
  Rule | Found? | File | Line | Status

SECTION 9: PHI DATA HANDLING AUDIT
  For every PHI table:
  Table | PHI Fields | Audit Logged? | 
  User Filter Always Applied? | Status

SECTION 10: UAT RESULTS
  Paste the full output from Step 8 here.

SECTION 11: RECOMMENDED ACTIONS
  Prioritised list of what to fix first,
  based on all findings above.

IMPORTANT NOTES
════════════════════════════════════════════════

1. Read the actual code files — do not guess
   or assume what the code does. Only report
   what you actually find in the files.

2. If a file does not exist yet (e.g. a route
   that was planned but not built), note it as
   MISSING in the report — do not pretend it 
   exists.

   using DATABASE_URL from environment. Make 
   sure the server is not running when you run
   it to avoid connection conflicts.

4. Mark any finding where data is read without
   a user_id WHERE clause as CRITICAL — this 
   means one user could potentially see another
   user's data.

5. Do not modify any application code during
   this exercise. This is read-only analysis
   except for creating the report file and 
   running the UAT script.
